# biliyt 归档可靠性修改方案

状态：三个批次的代码已实现。新增 3 个生产模块、3 个测试文件和 `repair` 命令；未新增运行时依赖或必填配置。下文保留原方案的分批设计，实际命令和恢复边界以 README 与 SOP 为准。

实施说明：主页历史同时保存独立 JSON 与 Markdown，修复旧快照不会覆盖最新主页；重建前会将旧库独有历史导出到持久化文件，移除目标的历史暂存于 `state/profile-history/`。首版字幕修复只生成独立文件，缺少嵌入字幕的媒体仍标为待重封装。已丢失的历史原始文件不以当前远程资料冒充恢复。验证范围为离线测试和本机 Windows 文件/SQLite 行为；尚未进行真实账号联网下载及 Linux 实机验证。

## 1. 目标与取舍

围绕现有 CLI 补齐五项能力：重建作用范围明确、历史可恢复、最终配置有效、索引与文件名解耦、缺失附件可补齐。

继续使用 Python、yt-dlp、本地文件和 SQLite，不新增运行时依赖。保留现有配置、下载目录、归档文本和主要命令。此次新增 3 个生产代码模块、3 个测试文件、1 个 CLI 命令、1 组状态展示；数据库不新增业务表，采用版本迁移扩展现有表和索引。

分三批实施。第一批可单独发布；第三批依赖第二批的产物清单。

## 2. 新增内容总览

| 类别 | 新增内容 | 作用 |
| --- | --- | --- |
| 代码模块 | `src/biliyt/atomic_io.py` | 在目标文件同目录写临时文件，再原子替换；统一处理 JSON、文本和字节写入 |
| 代码模块 | `src/biliyt/artifacts.py` | 保存每条内容的产物清单、实际路径、附件完成情况和索引状态 |
| 代码模块 | `src/biliyt/recovery.py` | 从清单生成修复计划，调用现有下载器、渲染器和索引函数补齐缺项 |
| CLI | `biliyt repair` | 预览或执行缺失附件补齐、索引重试 |
| 状态输出 | `status` 增加部分完成、待索引、待修复数量 | 显示已保存但尚未完整的归档 |
| 运行报告 | `run_id`、降级项、索引失败数、待修复数 | 让下载成功与附件完整度分别可见 |
| 归档文件 | 每目标 `.biliyt/manifests/` | 保存可迁移的逐条产物清单 |
| 归档文件 | `profile/snapshots/` | 追加保存主页历史及资产路径 |
| 数据库迁移 | 现有 `profile_snapshots` 增加稳定快照标识；`sync_runs` 增加 `run_id` | 防止重复重建产生重复历史 |
| 配置模型 | 内部局部覆盖模型与最终配置校验 | 保留未设置字段继承，校验合并后的交叉约束 |
| 测试文件 | `test_atomic_io.py`、`test_artifacts.py`、`test_recovery.py` | 验证持久化、清单和恢复行为 |

本方案不新增必填 YAML 配置，也不新增常驻队列进程。修复任务由持久化清单推导，避免维护另一套任务数据库。

## 3. 第一批：先修复确定性问题

### 3.1 重建作用范围

修改 `cli.py` 与 `db.py`：

- 首批保留 `--reset` 表示全库重建；同时传入 `--target` 时，在打开数据库写事务前报参数错误并退出。
- 普通 `db rebuild --target a` 保持增量导入行为，不清空其他目标。
- `db rebuild --reset` 改为先在同目录构建临时数据库；导入、完整性检查和计数核对成功后再替换。
- 重建、修复与同步共用现有进程锁，并将锁冲突提示改成“另一个写入操作正在进行”。
- 全库替换采用 SQLite backup 创建备份。关闭目标数据库连接并处理 WAL 后再替换，避免直接复制运行中的主数据库文件。
- Windows 下遇到其他连接占用时，保留原库并退出；替换失败时提供备份恢复路径。
- 导入阶段收集坏文件和失败条目；存在导入错误时，全库重建默认保留原库，输出失败清单。

本批先明确参数语义，暂不引入“删除单目标全部数据”的新命令。

验收：目标 a、b 同库时，组合参数被拦截且两者计数不变；重建中途异常时旧库仍可搜索；坏 JSON 有可定位的报告。

### 3.2 合并后校验配置

修改 `config.py`：

- 为可局部覆盖的配置引入内部 override 模型，保留 `model_fields_set`，不在局部配置上执行依赖默认值的跨字段规范化。
- 先按既有规则合并显式字段，再构造正式配置模型，执行类型、范围和跨字段校验。
- 校验时带上目标 ID 和字段路径，方便定位。
- 用户配置模型设置未知字段检查，拼错字段立即报错。
- 显式 `null` 只在原字段允许清空时表示清空；未设置继续表示继承。
- 日期格式和起止日期顺序在配置解析时校验。

示例：全局最短 300 秒、目标最长 60 秒应报配置错误。下层只覆盖最大休眠时间时，不应因局部模型默认值而改写其他显式字段。

兼容性：正确的现有配置保持原语义；此前被静默忽略的未知字段会开始报错，需在发布说明中标明。

### 3.3 立即暴露索引失败

修改 `downloader.py` 与运行报告：将静默吞掉的索引异常转为结构化警告，保留媒体下载成功结果，同时记录索引待重试状态。实际路径传递和重试执行在第二、三批完成。

## 4. 第二批：建立产物清单与可恢复历史

### 4.1 新增 atomic_io.py

提供内部函数 `atomic_write_text()`、`atomic_write_json()`、`atomic_write_bytes()`：

1. 在目标文件同目录创建唯一临时文件。
2. 写入、flush，按需要调用 fsync，然后关闭句柄。
3. 使用 `os.replace()` 替换目标文件。
4. 失败时保留原文件，清理本次临时文件。

接入失败队列重写、归档元数据重写、运行报告、JSON/Markdown 和清单写入。该模块保障单文件替换；多文件一致性由清单的最后提交状态表达。操作系统和文件系统对断电持久性的保证仍需在文档中说明。

### 4.2 新增 artifacts.py

新增内部数据结构：`ArtifactManifest`、`ArtifactStatus`、`DownloadResult`，以及管理清单的 `ArtifactStore`。

外部接口保持精简：读取条目清单、提交保存结果、列出待修复条目。临时写入、路径校验、状态转换和格式版本在模块内部处理。

清单存放于每个目标下载目录的 `.biliyt/manifests/<kind>/<安全编码后的条目标识>.json`。文件名标识使用确定性编码或哈希，原始 ID 保存在 JSON 中，避免原始 ID 中的路径字符造成问题。

拟议字段示例：

```json
{
  "schema_version": 1,
  "target_id": "yt_demo",
  "kind": "video",
  "item_id": "abc12345678",
  "source_url": "https://www.youtube.com/watch?v=abc12345678",
  "updated_at": "2026-11-28T11:00:00+00:00",
  "artifacts": [
    {"kind": "media", "status": "complete", "path": "示例标题.mp4"},
    {"kind": "metadata", "status": "complete", "path": "示例标题.info.json"},
    {"kind": "subtitle", "language": "zh-Hans", "status": "failed", "error": "HTTP 429"}
  ],
  "index_status": "pending"
}
```

设计约束：

- 本地路径一律相对目标 `download_dir`，使用 POSIX 格式；读取时检查路径仍位于归档根目录内。
- 按每个图片、每种请求的字幕语言记录状态，避免一个汇总布尔值掩盖局部失败。
- 状态区分 `complete`、`failed`、`pending`、`disabled`、`unavailable`、`unknown`。平台明确无字幕与网络下载失败分别处理。
- `write_info_json: false` 等显式关闭项记为 disabled，不循环修复；同时展示该选择对重建与搜索的影响。
- 清单只记录必要来源和脱敏错误，不保存 Cookie、代理凭据、临时签名媒体 URL 或完整请求头。
- 文件产物先写入，清单再提交；启动修复时重新检查文件是否存在。中断发生在写文件之后、提交清单之前时，允许通过磁盘检查重新对账。

媒体完成后继续写入既有 yt-dlp 归档记录；附件缺项通过清单保留，普通增量同步仍能跳过媒体重复下载。

### 4.3 根据实际路径索引

修改 `downloader.py`、`options.py`、`db.py`：

- 使用 yt-dlp 最终后处理阶段的信息获取实际产物路径，必须覆盖合并、转换与临时目录搬运后的结果。
- 支持一个入口产生多个分 P 结果，每个实际视频分别记录 ID 和产物。
- 索引直接消费实际元数据路径，不再依赖文件名包含 `[video_id]`。
- 索引成功更新清单；失败保留 pending/failed 状态及警告。
- 旧归档重建继续支持扫描 `.info.json`，通过内容 ID 识别条目。

验收：自定义模板、分组目录、分 P、临时目录和媒体格式转换均能建立索引。

### 4.4 保存历史并保证导入幂等

修改 `bilibili/archiver.py`、`state.py` 和 `db.py`：

- 主页每次采集生成稳定 `snapshot_id`，先追加写入 `profile/snapshots/<snapshot_id>.json`，包含采集时间、主页原始数据及头像/横幅相对路径，再更新最新主页文件。
- 运行报告生成 UUID `run_id`，报告文件名包含此 ID，避免同秒覆盖。
- 运行报告仍保存在 `state/reports/`，数据库重建新增从此目录导入运行历史的步骤。
- `profile_snapshots` 增加可空的 `snapshot_id` 及唯一索引；新快照按 ID 幂等导入。
- `sync_runs` 增加可空 `run_id` 及唯一索引；新运行报告按 ID 幂等导入。
- 旧快照、旧报告通过确定性内容标识导入，完全相同的历史去重；不按时间戳直接合并可能不同的记录。
- 历史 JSON 与最新主页 JSON 共同参与恢复，资产路径完整回填。

新增按版本执行的迁移函数，逐版记录到 `schema_migrations`。升级保留旧数据库的独有历史；重建前先合并旧库独有记录，迁移至持久化历史文件。仅剩最新主页文件的历史目录只能恢复其现存信息，已丢失的历史不作完整恢复承诺。

备份契约明确为：`downloads/` 保存内容和主页历史；`state/reports/` 保存运行报告；其余工作流状态也在 `state/`。完整备份需要同时包含两者。`db rebuild` 恢复数据库与索引，归档文本和失败队列继续由 StateStore 管理。

## 5. 第三批：增加补齐能力

### 5.1 新增 recovery.py 与 repair 命令

`recovery.py` 提供两个主要入口：生成 `RepairPlan`，执行计划并返回结果。通过现有下载器与 B 站客户端的真实差异设置内部接口，不引入通用插件框架。

拟议用法：

```bash
# 默认只预览，显示缺项、原因和是否需要联网
biliyt repair

# 只重试目标的索引，全程离线
biliyt repair --target yt_demo --only index --apply

# 按需补齐字幕和图片
biliyt repair --only subtitles,images --apply
```

命令参数：沿用 `--config`、可重复的 `--target`；新增本命令专用的 `--only index,metadata,subtitles,images`、`--apply`、`--limit`。`--limit` 限制本次处理条目数。

执行规则：

- 只读取归档和清单来生成预览；只有 `--apply` 执行写入或网络请求。
- 索引失败只补索引，不重下媒体。
- 字幕失败使用 yt-dlp 跳过媒体的能力；修复前识别媒体路径，避免重复下载主体。
- 图片失败保留原始来源；补齐后重新渲染对应 Markdown，再更新索引。
- 来源不可用时保留失败原因和最后尝试时间；本轮单条失败后继续其他条目。
- B 站鉴权错误或风控熔断终止本轮相关网络修复，保存进度。
- 初版只补齐独立字幕文件；已完成视频的嵌入字幕需求列为待处理状态，后续单独设计可回滚的重封装流程。
- 失败队列继续负责抓取失败；清单负责已保存条目的缺项，二者由 repair 统一读取并去重计划。

旧归档缺少清单时，通过已有 JSON 和磁盘文件建立基础清单；无法判断当时是否请求过的附件标为 unknown，默认不触发批量联网补抓。后续正常同步可补充明确状态。

### 5.2 状态和报告

扩展 `status` 与 `TargetRunSummary`：

- 保留原“新下载”和“失败”字段。
- 新增部分完成条目数、索引失败数、待修复条目数；同一条目在各列可能重叠，帮助文本明确说明。
- 字幕/图片失败不再只出现在即时日志中，报告包含缺项摘要。
- 媒体成功而附件失败显示为部分完成；CLI 使用已有部分失败退出码 2，便于定时任务感知。
- `repair` 全部完成返回 0，仍有失败返回 2，写锁冲突沿用 3，配置/参数错误返回 1。
